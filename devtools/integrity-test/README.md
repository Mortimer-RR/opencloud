# Upload-integrity torture test

Drives uploads through the real stack (proxy, ocdav, datagateway, storage-users with the
default `posix` driver and async postprocessing) of the upload-integrity fork, and checks
that every file either matches its source sha256 exactly or failed visibly and succeeded on
retry. **A file that exists with a wrong hash, at any point, is a failure.** The run exits
non-zero if any file is corrupt.

Local test use only: the server runs with a self-signed certificate, basic auth enabled and
a throwaway admin password (`.env`, generated by `run.sh`, git-ignored). Never point this
at a real deployment.

## Running

```sh
# 1. build the server image (vendored reva fork + forked web client)
WEB_DIR=/path/to/web-fork ./build.sh        # or WEB_DIST=/path/to/web-fork/dist

# 2. for the desktop scenario: a desktop-build image and a volume with a built client
#    (see the desktop fork's FORK_NOTES.md), names overridable with
#    DESKTOP_IMAGE / DESKTOP_BUILD_VOLUME

# 3. run
./run.sh                    # all scenarios
./run.sh baseline overlap   # selected scenarios
./run.sh --down             # remove containers and volumes (incl. the ~6 GB corpus)
```

Reports are written to `results/report-<timestamp>.md`. The latest full run is in
`RESULTS.md`.

The server image is `IMAGE` from `.env` (default `opencloud-integrity:dev` from `./build.sh`).
To test a deployment image, set e.g. `IMAGE=opencloud-integrity:integrity-<commit>` there.

Requirements: Docker (Linux containers) with access to `/var/run/docker.sock`, about 25 GB
of free disk (corpus, uploaded copies, versions), and network access for the images.

## What it does

The corpus (cached in the `integrity_corpus` volume): random files of 0 B, 1 B, exactly
the tus chunk size (10 MB), chunk size + 1 B, 100 MB, 1 GB and 5 GB, plus two files with
the same name, size and mtime but different content (`twin-a/twin.bin`, `twin-b/twin.bin`).

| # | Scenario | How |
| --- | --- | --- |
| 1 | `baseline` | every corpus file via tus and via plain WebDAV PUT, 20 concurrent |
| 2 | `netem` | `tc netem loss 5% delay 200ms` on the client, files up to 100 MB (1 GB and 5 GB would take hours) |
| 3 | `overlap` | 1000×: PATCH, and while it is still streaming HEAD + PATCH part of the rest from the returned offset; then the first request sends the rest of its body while the upload is still open; then finish from the server offset. Without checksum, like browser uploads before fix 5 |
| 4 | `crash` | `kill -9` the server mid-upload, restart, resume. Then with a 20 s postprocessing delay: upload, kill during postprocessing, restart, `uploads sessions --resume` |
| 5 | `proxy` | through nginx with request buffering on (default) and `proxy_read_timeout 5s` |
| 6 | `restore` | restore versions of a 1 GB file (two versions with different mtimes) while 10 readers download it in a loop; every download must hash to one of the two versions |
| 7 | `aborted` | v0 finalized; upload A held in postprocessing (1 h delay); upload B finalized; A aborted with `uploads sessions --id A --clean`. B must survive, A's version must remain |
| 8 | `desktop` | `opencloudcmd` syncs through a fault proxy (`chaosproxy.py`) that holds back one completed PATCH response past the client's 5 min timeout, drops two PATCH connections and corrupts one byte of one upload. The corrupted upload must be rejected (460) and then succeed. Up to 4 sync rounds 30 s apart, as failed items are retried after the client's error blacklist delay |
| 9 | `web` | headless Chromium (Playwright) uploads the corpus through the web UI; one upload with a tampered checksum must be rejected; the same-fingerprint resume splice (twins) must not be stored. The test server uses OpenCloud's default CSP, so this exercises the JavaScript SHA1 fallback |

Each scenario deletes its uploads and empties the trash after it is verified
(`KEEP_UPLOADS=1` keeps them).

After each scenario every file is downloaded via WebDAV and compared by sha256 with the
source, and the stored `oc:checksums` SHA1 is compared too. Files still in processing are
waited for (up to 15 min) and reported as stuck. Sessions still in processing at the end
are listed (`opencloud storage-users uploads sessions --processing`).

`IMAGE=<image:tag> ./run.sh ...` runs against another image, e.g. one built from
unmodified upstream to see the scenarios fail (the server is recreated with the same image).

A file with correct content but no stored checksum is counted as matched and listed with a
note (0-byte files never get stored checksums).

## Deviations from the handoff

- Crash: the whole server process (all services, including storage-users) is killed, not
  storage-users alone. Running storage-users in its own container would mean rebinding
  every internal service address. Killing everything is a strictly harsher crash.
- Netem: only the client's egress is shaped, and the 1 GB/5 GB files are skipped.
- Desktop: the client's HTTP timeout is fixed at 5 minutes in `opencloudcmd`, so one real
  timeout is forced (≈5.5 min); the other faults are dropped connections.
